Unified Observability for Traces
High-Level Architecture · with Batch

End-to-end telemetry pipeline that carries customer-facing traces, metrics, and logs from Core FD & Near-Core services through the CDP FD Ingestion Platform into a multi-tenant Data Cloud Lakehouse — combining a real-time streaming path and an S3-backed batch path for consumption by Unified Observability and headless.

Supported today: Traces & Error Logs. Metrics is planned future work.

Reference Architecture

Service / Compute Store / Sink Telemetry ingest Real-time / streaming Planned: Batch (S3 → Spark) Query experience layer
⚡

Two coordinated paths, one lakehouse. Structured signals — traces and error logs today (metrics planned) — travel the real-time streaming path (Beacon → tenant-sharded Ajna Topics → Observability Multi-Tenant Streaming connector → fan-out writes). High-volume Info Logs take the batch path (Ajna → Amazon S3 → Single-Tenant S3 Spark job → Lakehouse). Both converge on the per-tenant Data Cloud tables that power Unified Observability and headless access.

02

How the Data Flows

STEP 01 · INSTRUMENT

Core & Near-Core emit telemetry

Event Monitoring instruments Flow, APEX, Prompt Builder and Near-Core services (DC, Planner, LLMG, MCP), producing customer-facing telemetry.

STEP 02 · INGEST

Ingestion Service → Ajna

Telemetry lands in the Ingestion Service (part of the Ingestion Platform) inside CDP FD and is funneled into Ajna, the ingestion backbone.

STEP 03 · SPLIT (STREAMING)

Traces & Error Logs → Beacon

Ajna routes structured signals to Beacon inside Falcon Instance 2, entering the real-time path for low-latency processing. Traces and Error Logs are supported today; Metrics is planned future work.

STEP 03 · SPLIT (BATCH)

Info Logs → Amazon S3

High-volume Info Logs are written to Amazon S3, decoupling bulk log storage from the latency-sensitive streaming path.

STEP 04 · SHARD

Ajna Topics, sharded by CDP tenant

Beacon publishes to Ajna Topics sharded by CDP Tenants, preserving multi-tenant isolation as data enters Data Cloud.

STEP 05 · STREAM

Multi-Tenant Streaming connector

The Observability Multi-Tenant Streaming connector consumes the sharded topics and performs fan-out data writes into the per-tenant Lakehouse tables.

STEP 06 · BATCH LOAD

Single-Tenant S3 Spark job

A Single-Tenant S3 Spark job reads logs back from S3 and loads them into the corresponding Data Cloud TenantN table — a per-tenant batch write.

STEP 07 · CONSUME

Lakehouse → Unified Observability & headless

The Consumption Layer queries the Lakehouse: Unified Observability for analytics and headless for conversational, agentic access.
